# S6 heartbeat measurements

Measurements were collected on 2026-11-05 on an Intel Core Ultra 9 285
with 24 cores, Linux 6.17.0 and Python 3.12.3. The release build used Rust
1.98.0. Database files were on the same ext4 filesystem for both targets.
Every native and Python commit used `FULL`. The host was shared, so the
results remain provisional.

The final comparison pins the reference server and its managed child to
CPUs 0 through 1, and the constrained server to CPU 0 with CPUQuota 100%
and MemoryMax 512 MiB. Four client processes use CPUs 4 through 7 outside
the server allotment. Each comparison uses the same S6a payload, connection
close, 1 ns think time, initial database with no events and two enrolled
nodes. The reference and constrained measurements last 30 seconds after
5 seconds of warmup. Mixed measurements last 15 seconds after 3 seconds of
warmup. The connection-capacity measurements last 5 seconds after 1 second
of warmup. Every attempt is retained by the S6a harness.

Commands are the `heartbeat.py` examples in README.md, with
`--server-cpus 0-1 --client-cpus 4-7` for reference, mixed and 256 clients,
and `--server-cpus 0 --client-cpus 4-7` for the constrained comparison.
Use the matching release binary with all four native families enabled.
Raw reports are kept under the output directories selected by the operator.
The tables below retain slower runs and errors, including the exploratory
runs before affinity and separate workload credentials were set.

## Qualification

At 32 clients in the 1-vCPU, 512-MiB allotment, the final candidate produced
4,854.93 and 4,412.13 OK writes/s. Across the two equal windows, that is
4,633.53 OK writes/s versus Python 148.10, or 31.29 times Python. The aggregate
is 0.73% above 4,600/s, and one individual run is below the target. The final
64-client reference repeats are below 4,600/s. Throughput qualification is
left open for the conductor rather than treating the aggregate as a
repeatability claim. Native p99 is below 250 ms in these runs, and both final
256-client runs have zero transport errors and zero refused connections.

## Results

The `head` phase includes the inclusive 8 MiB body-budget fix and the session
control-key and unhashable-action compatibility fallbacks. Its reference and
constrained runs use 15 seconds after 3 seconds of warmup, mixed runs use
8 seconds after 2 seconds, and 256-client runs use 3 seconds after 1 second.
The longer `pinned` phase precedes those two parity fixes. `exploratory` uses
8 seconds after 2 seconds, no affinity and, in its first runs, one shared
credential. Its errors include credential-cap shedding and lock contention.
Those observations are retained and are not used as quiet-hardware proof.

Python's global handler cap produces many transport errors at 64 and 256
clients. The native event credential has a 64-request allowance, so HTTP 503
answers at 256 clients are expected admission shedding. A 503 is an accepted
connection. All latency percentiles in this table include failed attempts, as
S6a requires. The JSON report records transport errors separately where the
harness version exposed them.

## Mixed contention

Lock wait is the sampled last-batch gauge, in milliseconds. It includes the
arbiter and SQLite BEGIN wait. COMMIT p99 is a cumulative histogram bucket
upper bound. Python cold writes can return `database is locked` while native
batches repeatedly acquire the write lock. These errors are retained in
`S6.json`, alongside every background attempt in the local raw reports.
