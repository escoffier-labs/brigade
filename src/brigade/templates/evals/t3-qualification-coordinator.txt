Coordinate the single governed native T3 batch described in expected.json.
Run the shell commands from this private arm directory:

    cd $folder
    cat $read_expected

Use the designated T3 parent on Codex gpt-6.2-sol, medium reasoning and
serviceTier=default. The parent must be attached to the workload checkout at
the expected base. Call T3 tools yourself. Keep the raw replies in this
directory. Edit only the evidence files named here. Wait for completion wakes
and let the operator handle worker approvals.

## Launch

1. Use the exact orchestrator_capabilities reply for this parent thread.
   Call it if this thread has not already captured it. Otherwise copy its
   original reply from the previous arm after confirming the same parent and
   provider settings still apply. Save the exact reply as capabilities.json.
   Match parentThreadId to expected.json and confirm the expected environment,
   project and provider instance. Create capabilities-report.json with schema
   brigade.t3_capabilities_report.v1, origin_environment and origin_project
   from expected.json, reported_at set to the current UTC ISO 8601 timestamp
   with Z, and capabilities set to the unmodified tool result. Immediately run:

       $ready > readiness.json

2. Mark immediately before the open command, and check open.json against
   expected.json for the run ID and all three task IDs.

       $mark opened
       $open > open.json

3. Mark native delegation start once before claiming any tasks.

       $mark delegate-start

4. For each task ID in sorted order, substitute that task ID for TASK and
   complete these steps in order.

   a. Claim the task and check the run, task, seat and request identities in
      the claim receipt.

          $claim TASK > claim-TASK.json

   b. Call delegate_task with exactly the JSON object at delegate_task in
      claim-TASK.json. Save the exact tool reply to delegate-TASK.json.

   c. Mark the reply immediately after saving it. If that task's wake arrives
      while saving the reply, finish saving it and writing this mark before
      handling the wake.

          $mark delegate-reply-TASK

   d. Record acceptance.

          $accepted TASK --native-json delegate-TASK.json > accepted-TASK.json

5. After recording all acceptances, mark launch complete if
   delegate-replies.json is missing.

       $mark delegate-replies

   Mark launch complete before finalizing, even if all tasks are already
   acknowledged. Once delegate-replies.json exists, finalize using the
   commands in the wake section if all tasks are acknowledged. Otherwise
   end the turn and wait for the remaining wakes.

### Resume launch

On resuming, continue at the first unfinished sub-step for each task. A
sub-step is finished when its output file exists. Check claim-TASK.json,
delegate-TASK.json, delegate-reply-TASK.json, and accepted-TASK.json in
that order. Never re-run a sub-step whose output file exists. Apply the
same rule to single marks. Skip a mark only when its own file already
exists. Check opened.json for opened, delegate-start.json for delegate-start,
delegate-replies.json for delegate-replies, and wake-TASK.json for wake-TASK.

## Each completion wake

Wakes can arrive while the launch turn is still running. Handle each wake
after saving that task's delegate reply and its per-task reply mark, even
when other tasks have yet to launch. When returning to launch, continue
at the first unfinished sub-step for each task. Use the saved output files
to skip completed sub-steps and marks as described in the launch section.

1. Check the waking task ID against its saved delegate reply. If it was already
   acknowledged, check the task and run IDs. Resume launch if needed or end
   the turn. For a new wake, skip the wake mark if wake-TASK.json already
   exists. Otherwise record the mark immediately.
   Substitute the waking task ID for TASK and run:

       $mark wake-TASK

2. Ensure the waking task's acceptance is recorded before observing it.
   Call task_status once for the delegate reply's taskId. Save the exact
   reply to status-TASK.json. Call t3_thread_read for its childThreadId with
   view=activity and limit=100. Save the exact reply to activity-TASK.json.
   Require hasMore=false. The child run in recentRuns matching the terminal
   run in task_status supplies startedAt and completedAt. A missing or
   ambiguous match blocks the measurement.
3. Observe the exact status reply and check that the observation is completed.
   Verify the JSON answer against answers.TASK in expected.json, and check
   that the child activity identifies a distinct worktree with clean Git status
   at the pinned base. Ack the exact result_id from the observation.

       $observe TASK --native-json status-TASK.json > observe-TASK.json
       $ack TASK --result-id RESULT_ID > ack-TASK.json

4. Never finalize before delegate-replies.json exists. If it is missing,
   resume launch and complete the launch mark in step 5. Once that file
   exists, end the turn if any acknowledgements are outstanding. When all
   three tasks are acknowledged, finalize, check the completed status, then
   run the independent evidence check. The finish command writes
   measurements.json atomically.

       $finalize > finalize.json
       $finish

## Exceptions

Stop on a failed command, ambiguous reply, or unverified result. Preserve the
raw files. Record the failed step and exact error with the following command
and stop. A failed batch stops the campaign, and an operator handles closeout.

    $abort 'FAILED_STEP_AND_ERROR'

For an intervention outside Brigade's cancel and hold facts, append one JSON
string describing the action to interventions.jsonl. Log independently
observed errors as one JSON string each in errors.jsonl. Record no prompts or
secrets in either log. Keep any operator approval wait inside the measurement.
