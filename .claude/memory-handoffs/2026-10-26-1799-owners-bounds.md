# Memory Handoff

## Type

bugfix

## Title

Bound ownership-map metadata and active claim materialization

## Summary

A valid principal-heavy ownership policy produced a JSON response larger than the client's cap because principal names appeared twice and metadata was outside the response budget. The ownership map also materialized expired claim history before applying its source limit. Owner metadata now shares the byte budget, and a separate bounded active-claims reader filters before its SQL limit.

## Durable facts

- Keep enriched principal records once, outside `match`. Reserve omitted-owner names before filling metadata in name order; expose `owners_total` and `truncated_owners` while preserving the original view's charters.
- JSON cost uses the same ASCII escaping and separators as response serialization. Metadata and holdings share the 480 KiB budget, below the client's 512 KiB limit.
- Owners request `SOURCE_LIMIT + 1` active claims so the extra row signals truncation. Filter expiry before limiting, validate every fetched generation fence, and reject non-positive or non-integer limits.
- This bounds rows fetched into Python, not database scanning complexity. No index or schema change is claimed.
- General `list_claims` still validates expired fences; mutation and authority paths are unchanged. No test assertions were weakened.
