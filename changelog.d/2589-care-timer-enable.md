- `brigade care install` on systemd now links each timer it writes into `timers.target.wants`, runs `systemctl --user daemon-reload`, and starts every newly linked timer so the schedule fires on a running host. A reinstall that rewrites an already-linked timer reloads and restarts it so a changed schedule takes effect. A missing or failing systemctl keeps the link and prints the exact `daemon-reload` and `start` commands. `--no-enable` writes unit files only and `--dry-run` reports the planned per-timer action without calling systemctl.
- `brigade care install` reports an already-linked timer as enabled even under `--no-enable`, treats a foreign or symlinked `timers.target.wants` as a conflict and writes nothing, and never replaces a foreign entry.
- `brigade care uninstall` stops each timer whose link it removes (a not-loaded unit counts as stopped) and removes the `timers.target.wants` link it created, but only a symlink to the unit being removed. Foreign entries are left alone and a symlinked `timers.target.wants` is never followed.
- `brigade care status`, `brigade work brief`, and `brigade doctor` warn when an installed timer is disabled, when an enabled timer has never recorded a receipt one schedule period after it was enabled, and when runbook entries run with `brigade extras` off. They read systemd units, LaunchAgents plists, and a readable crontab spool file without a subprocess, and say a backend was not inspected instead of reporting it healthy. The `care status` aggregate `enabled` is false while an installed timer is disabled.
