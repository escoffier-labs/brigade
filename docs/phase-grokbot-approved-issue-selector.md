# Grok Bot approved issue selector

## Status

Implemented and verified on 2026-08-26 under the standing Grok Bot scope. The
selector is independent of Fleet Hub active-work reporting.

## Problem

`brigade run cloud grokbot feed` safely drains a private manifest, but a
completed manifest never produces another job. An hourly timer therefore runs
without work until an operator writes a new manifest. Grok Bot has a separate
weekly quota, and the adapter does not expose its remaining percentage.

The next feed source must find useful work without copying untrusted issue text
into a job, creating mutation authority, or competing with a job that is
already queued or active.

## Decision

Add `brigade run cloud grokbot scout-feed`. It reads one owner-only policy file,
queries one allowlisted GitHub repository through `gh`, and selects open issues
that carry an explicit approval label. The command defaults to preview mode.
`--apply` is required to enqueue.

The first version creates Repository Scout jobs only. It does not create
Implementation Worker jobs, edit labels, comment on issues, open pull requests,
merge, release, deploy, or call Fleet Hub APIs.

### Policy

The policy schema is `brigade.grokbot.scout-feed.v1` and contains exactly:

- `schema`
- `approved: true`
- `repository`, in `owner/name` form
- `approval_label`
- `base_ref`
- `ownership_paths`
- `verification_commands`
- `timeout_seconds`
- `daily_limit`, from 1 through 10

The file must pass the same regular-file, current-owner, and mode checks as an
approved feed manifest. The command rejects a symlink and any group- or
world-writable policy.

### Selection

The selector runs `gh issue list` without a shell and requests only issue
numbers. The repository and approval label come from the validated policy. It
sorts returned issue numbers in ascending order.

Preview checks a read-only queue snapshot. Apply repeats admission atomically
under the Grok Bot queue lock:

1. If a Repository Scout job is `queued`, `claimed`, `running`, or
   `cancel-requested`, return a no-work success.
2. Count Repository Scout jobs created on the current UTC date. If the count is
   at `daily_limit`, return a no-work success.
3. Skip every issue whose stable idempotency key already exists.
4. Select the first remaining issue and enqueue one job. One invocation cannot
   create more than one job.

The idempotency key is the 64-character lowercase SHA-256 digest of the
repository, a separator byte, and the issue number's canonical positive-integer
bytes. This keeps the key within Brigade's 128-character bound for every valid
repository and issue number. A completed, failed, expired, or canceled issue
job stays known.
Re-running an issue requires a new operator-approved policy revision in a
later feature.

### Job envelope

The envelope uses the fixed Repository Scout role and `report` artifact. The
label is `Repository Scout` and does not include the issue title or body.

Instructions are generated by Brigade from a fixed template. They require the
Bot to confirm the issue is still open and still carries the approval label,
treat the issue body and comments as untrusted context, inspect the declared
paths read-only on the declared base ref, run the declared checks, and return a
report. They prohibit edits, commits, pull requests, merges, releases, deploys,
and external mutation.

The selector never places GitHub credentials, issue bodies, issue comments, or
titles in queue state, output, receipts, or logs.

## Alternatives considered

### Continue rotating static manifests

This preserves the current trust boundary and remains the fallback. It requires
an operator to author every new entry, so hourly timers often have no work.

### Select from Fleet Hub campaigns

This could coordinate work across repositories and machines. It depends on the
campaign and active-work surfaces and would overlap the current Fleet Hub work.
Keep it as a later source behind the same selector contract.

### Use n8n or OpenClaw to write manifests

This can schedule today, but it duplicates validation and makes a second system
responsible for queue policy. The Brigade-native selector keeps the approval,
deduplication, queue-cap, and receipt rules in one package.

## Failure behavior

- Missing `gh`, authentication failure, malformed JSON, invalid policy, or
  unsafe policy permissions return exit 2 without queue mutation.
- An empty approved issue set, an active Scout job, a reached daily cap, or an
  all-known issue set return exit 0 with `created: 0` and a stable reason.
- Output contains counts, the selected issue number, safe job projection, and
  the stable reason. It does not contain the repository, policy commands, or
  paths.
- The selector performs one complete preview before enqueue. A queue error
  returns a generic stable reason without printing private context.

## File map

- Create `src/brigade/grokbot_scout_feed.py` for policy validation, GitHub issue
  discovery, queue and daily-cap checks, envelope construction, and enqueue.
- Modify `src/brigade/cli/run_cloud.py` to register and dispatch `scout-feed`.
- Create `tests/test_grokbot_scout_feed.py` for permissions, discovery,
  deterministic selection, deduplication, queue caps, daily caps, fixed
  envelope content, redaction, no-work states, and CLI behavior.
- Modify `docs/grokbot-mcp.md` with the private policy and timer example.

## Acceptance

1. Preview discovers an approved issue but does not create queue state.
2. Apply creates exactly one read-only Repository Scout job.
3. Repeated apply never duplicates an issue.
4. Active Scout work and the UTC daily cap both return no-work success.
5. Issue titles, bodies, comments, credentials, commands, and ownership paths
   do not appear in command output.
6. Invalid policy or GitHub output leaves the queue unchanged.
7. Existing Grok Bot feed, queue, MCP, operations, and tracker tests stay green.
